Virginia Rules Workbench: admin mockups

An admin tool where policy staff and engineers change the Virginia return together. Policy staff edit values and rules in plain language. The tool writes the XML in facts/virginia.xml, and every change goes through worked examples, a plain-language diff and two sign-offs before it ships.

Static mockups. Tax year 2024 values come from facts/virginia.xml. The 2025 values, the people and the change request are invented to show how the work flows.

Why it looks like this

  • Organized by form line and statute, the two things policy staff look things up by. The fact path (/vaLotterySubtraction) only shows up in the engineer's view.
  • Federal lines are visible but locked. Only virginia.xml and virginiaLocalities.xml can be edited, because the federal modules must stay byte-for-byte copies.
  • The status pill tells everyone who is touching what, so two people don't edit Line 11 at once.
  • The tax year switcher picks which <TaxYear> values you see and edit.

Why it looks like this

  • A column per tax year fits how the law changes: by year, and usually just the number. Behind the scenes each cell is one <Fact> with a <TaxYear>, like /vaStandardDeductionSingle.

3. Rule editor: rules and exceptions as fill-in sentences

Why it looks like this

  • Only sentences that convert cleanly to code. “If / Except if / Otherwise” is a <Switch>, “minus” is <Subtract>, “but no less than” is <GreaterOf>. There's no free-text formula box.
  • Exceptions are checked first. Authors write them under the rule, the way a statute reads, but they become the first <Case>s, since the first match wins. The blue tag says so. Drag handles order several exceptions among themselves.
  • The XML panel is the same rule, not a copy. That's what lets AK and MT work on one thing: either one can edit it, and the other view updates.
  • The search hits a wall, and the tool shows it. Direct File has no W-2G facts, so MT files request #4 (screen 6). The blank becomes a purple Requested chip, and the draft can be saved but not reviewed until engineering finishes.
  • “Because” is required on every exception. It becomes the XML comment and appears in review.
  • Federal facts in the search are only those ADR-001's integration rule allows: exported to states or on MeF.

5. Review & approve: two keys, one change

What a reviewer sees. The plain-language summary and the XML diff are generated from the same edit. A policy reviewer signs off that it matches the law, an engineer signs off that the code is sound, and only then does it merge. Underneath this is a pull request, but nobody on the policy side ever has to see one.

Why it looks like this

  • The plain summary comes first for the policy reviewer. The XML diff is right below it for the engineer. Both come from the same edit, so they can't disagree.
  • The tool writes XML in one fixed format, so a value change is a two-line diff, not a reformatted file.
  • Two different approvals, each with its own question: “is it the law?” and “is it sound?”. The author can't approve their own change.
  • The comment thread shows the collaboration working. The engineer asks for an example, not a code change.
  • The checks are the repo's own: schema, examples, parity, Spanish, axe.

6. Ask engineering: when the rule needs something new

Level 3. A new question for the filer means new screens, English and Spanish text, accessibility work and tests, so policy staff don't build it. They write the request in their own terms, and the request becomes the engineer's spec. An AI draft can help fill it in, but a person confirms every field.

Why it looks like this

  • The boundary is explicit. Policy staff can change values and logic. A new writable fact touches flow, both locales and accessibility, so engineers own it.
  • The request is a spec: the law, the wording, the answer type and failing examples. Engineering's done-condition is “the examples go green”.
  • AI is marked as a draft with its own color, and it only fills in fields. It never writes XML, and its output goes through the same review.
  • The loop closes back in screen 3. Once the fact exists, the author finishes their own rule.
