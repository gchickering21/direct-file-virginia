Virginia Rules Workbench: from a law change to the filer's screen

The first set of mockups (rules-workbench.html) lets policy staff change a value or a rule and send it through two approvals. These six screens pick up where that set stops. A change starts from the law rather than from a file; it carries the tax years it applies to; and when a new rule needs a question the return does not ask yet, the policy author writes the question, the screen and the words, and the tool writes the fact, the flow page and the locale keys. What reaches the filer's screen is authored by the person who read the law, not by a request to engineering.

Static mockups. The 2024 values come from facts/virginia.xml. The 2026 Act, its chapter number, the people and every 2026 figure are invented to show the workflow; they are not Virginia law or Virginia Tax staff. The two step changes on screen 2 (the refundable earned income credit rate and the military benefits cap) are the real ones the 2024 facts already cite.

1. Start from the law: one change, fanned out

A law change rarely touches one thing. The author pastes the section, says when it takes effect, and the tool proposes the edits it implies: a value, an exception, a new question, some wording. The author keeps or drops each one. What survives becomes a single change with several parts, reviewed together.

Why it looks like this

  • The unit of work is the law change, not the file. One Act becomes one change with three parts, one review, one pull request. Today each part would be its own draft.
  • The effective date is asked up front because it decides everything downstream: which column on the values table, which site build carries it, and when the filer sees it.
  • AI proposes; it does not write. The purple band is a checklist the author edits. Each row links a highlighted phrase in the law to a rule the tool already knows. Nothing goes into XML from here.
  • The boundary is on the page. The fourth row is something the return cannot do yet. It becomes a request to engineering, as on screen 6 of the first set, and is kept out of this change so the other three can ship.
  • Keeping the pasted text means every published rule can point back at the words that made it. The return can later explain Line 13 to a filer by citation.

2. Tax years and effective dates: the law changes by year

Most law changes are “for taxable years beginning on or after”. Some step, some sunset. The values table gets a column per year, a value either is set by a law in that year or carries forward, and the author sees which filing season's site will carry the change.

Why it looks like this

  • Columns are tax years because that is how the Code is written. “Carries forward” is the default, so a change is one cell, not a whole row.
  • Sunsets are visible. The 15% rate ending after 2024 and the $30,000 cap ending after 2024 are real, and both are already in the 2024 facts' descriptions as prose. Here they are data.
  • The season panel answers the question policy staff actually ask: when will a filer see this? The effective year picks the site build; approval timing does not.
  • Honest about the engine. <TaxYear> is in the Fact Dictionary 3.1 spec and on every Virginia value fact, but nothing in Form Builder or the engine reads it today. The build has to select facts by year (or the tool writes one values module per year). That is engineering's one-time piece; the table above does not change either way.
  • The XML tab is the same value as code. One fact per year it was set, each with its own citation, so the history is in the file and not only in the tool.

3. Question builder: an exception that needs something the return does not know

Subdivision b lifts the cap when the account's beneficiary has a disability. Nothing on the federal return says that, so the rule needs a new question. In the first set this was a request to engineering. Here the author answers five things, sees the screen as the filer will, and the tool writes the fact, the flow page and the locale keys. The new answer is in the rule editor's picker at once.

Why it looks like this

  • Five answers, five artifacts. The wording becomes the fact's name and the screen's heading; the answer type becomes <Writable><Boolean/>; “who gets asked” becomes the screen's condition; “where” is the position in your-taxes-virginia.xml; the help text becomes locale keys. Nothing the author types is free-form code.
  • This is Author Mode's backend, asked in plain words. Form Builder already has /author/create-fact and /author/create-screen, which write the XML and regenerate the site in process. The builder is a form over them with the policy vocabulary on top.
  • The preview is the real page. The site regenerates from the draft files into a preview folder; the right-hand panel is that page with a demo household loaded, not a picture of one.
  • The style guide runs as you type. Direct File's content guide (one question, “you”, present tense, no jargon) is a lint here. The “beneficiary” warning is the kind of thing a content designer would catch; the tool catches it first.
  • “Who gets asked” does double duty. It gates the screen and it protects the rule: a rule may only read an answer from someone who was asked. The tool refuses a rule that reads the fact outside that condition.
  • Spanish is never auto-published. The key is created with the English in it and flagged. Screen 4 shows what happens next.
  • The exception is written straight away. No purple “Requested” chip, no waiting. The new fact shows as Asked in the picker the moment the builder saves.

4. Words on the screen: English, Spanish, and numbers that never go stale

Behind the words engineer's view

Locale keys are hashed from the English, so a changed sentence is a new key: p-f42bed → p-91c0e4. The tool moves the Spanish to the new key and marks it stale, instead of dropping it.

The transpiler regenerates flow_en.yaml; virginia_es.yaml is the hand-written file merge-virginia-es.py folds in, as today. The “needs translation” flag is a comment in that file.

Why it looks like this

  • Edit where the filer reads it. The author sees the paragraph, not a YAML key. The key, the hash and the merge are the engineer's panel.
  • Numbers bound to values is the one change that makes next year's update smaller than this year's. A typed “$4,000” is a bug waiting for 2026; a chip that renders the value is not. The tool finds the typed ones and offers to bind them.
  • Spanish is a third approval, only when words change. A translator is a role beside author, reviewer and engineer. The English can be approved while the Spanish is pending, but the change cannot publish until both are in, because the Spanish site is the same build.
  • Stale, not missing. Content-addressed keys would otherwise orphan the Spanish the moment the English changes. Carrying it to the new key and flagging it keeps the translator's work and shows exactly what is out of date.
  • Direct File's own experience: Spanish lagged English for a season. Making the lag visible on the author's screen is the fix a tool can offer.

Why it looks like this

  • One page for the footprint. Values, rules, screens, words, examples, federal files: six numbers a reviewer can read in ten seconds. The red one is the one that blocks publishing.
  • Examples are the contract. The author wrote “Savers, $9,000, beneficiary with a disability” from subdivision b before the rule existed; it went green when the rule was right. That is the same discipline as the first set, now covering a question too.
  • The age row is a trap the tool catches. Adding a question adds an input to every example. Defaulting it to No keeps 41 examples honest, and the one where a different exception already applies is flagged for the author to confirm rather than silently passed.
  • Before and after are real pages from two builds: the live 2025 site and a preview regenerated from the draft. The preview URL is what goes to the reviewer and, if Virginia Tax wanted, to a usability session.
  • “0 federal files touched” is the ADR's rule as a check. The tool cannot write outside virginia.xml, virginiaLocalities.xml, the Virginia flow and the Virginia locales.

What “Roll back” does

It starts a new change that reverts this one, with the same checks and the same signatures. Nothing is deleted from history, and the 2026 build only moves when that change is published. A change that has already reached filers is never edited in place.

Why it looks like this

  • The pull request is the audit trail, but nobody on the policy side sees GitHub. The tool opens it with the plain summary as the description and the three approvals as its required reviews. The repo's own checks (make virginia-check, virginia-cases, virginia-a11y) are the PR's checks.
  • The effective year, not the approval date, decides when filers see it. Publishing puts it in the 2026 season build. If the Act had been retroactive to 2025, the tool would say the 2025 site rebuilds and ask for a second look.
  • Three signatures, each with one question, and the translator's only when words change. Routine value changes stay at two.
  • Rollback is a change, not a button that edits history. That matches how a tax agency has to think about a rule that already reached returns.
  • The history panel, with the Act's text kept from screen 1, is what lets the return answer “why is my Line 13 $5,000?” by citation years later.
